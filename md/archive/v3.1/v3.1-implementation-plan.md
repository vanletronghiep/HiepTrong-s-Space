### 7.2 Recurrence and precedence

New classes repeat weekly by default with Set Default checked. Uncheck to create a single-week entry. Recurrence ends on an optional inclusive end date, otherwise continues until explicitly ended. A series has a stable identity; an occurrence has a stable original-week identity that survives a time/title edit.

Resolve an occurrence in this order:

1. Determine whether the series exists for the original week, considering start/end limits and a series deletion cutoff.
2. Choose the latest default revision effective at or before that week.
3. Apply the explicit weekly override, if any, including cancellation or deletion for that occurrence.
4. Apply a series-wide cancellation cutoff where present. Cancellation from a week onward must not be undone accidentally by a preexisting later default or weekly override.
5. Derive effective dates, fields, status, visibility, and cell occupancy. Deleted occurrences are absent; canceled occurrences are visible but do not occupy an active slot.

| Action | Required effect |
| --- | --- |
| Edit existing class, Set Default unchecked | Change only the selected occurrence; other weeks remain unchanged. |
| Edit with Set Default checked in week A | Add/replace a default revision effective in A and remove A's redundant override. Preserve earlier weeks and other weekly overrides. |
| A later default already starts in week B | Preserve it. The change at A applies until B, not beyond B. |
| New class, Set Default unchecked | Create one dated class; do not generate future occurrences. |
| Cancel This Week Only | Preserve this occurrence with canceled status, without changing other weeks. |
| Cancel This Week Onward | Preserve future occurrences/history but mark the series canceled from this week onward, including already-customized future occurrences. |
| Delete This Week Only | Suppress only this occurrence; it must not reappear from the recurring default. |
| Delete This Week Onward | End this series before the selected week and remove its future overrides. Preserve earlier weeks and unrelated replacement classes. |
| Explicitly correct a past occurrence | Allow the individual correction. Later default changes still cannot rewrite prior weeks. |

- Canceled occurrences remain in relevant Upcoming, Past, and Week Calendar views, clearly marked; exclude them from active counts, Highlights, and active-cell conflicts. Cell/history relationships must remain accessible when a replacement is displayed.
- Check all affected future default segments and finite overrides before saving. The 12-week rendering horizon is not a limit on conflict validation. For indefinitely repeating schedules, compare weekly slots over overlapping effective date intervals rather than generating infinite occurrences.
- Preserve future overrides even when a newly inserted default changes title, weekday, period, or highlight status. Store enough effective data in overrides to keep them stable; do not retain only a fragile patch whose meaning changes underneath it.
- Date edits retain the occurrence's original-week identity, even if its actual date moves into another week. Query overrides by actual dates as well as original week so moved classes cannot disappear from the destination calendar. Scope labels identify the original occurrence when it differs from the displayed date; a move does not silently edit the destination week's separate occurrence.
- Optional end-date changes are part of recurring scope; extending/revising defaults must not revive deleted or canceled occurrences silently. Preexisting later defaults and explicit overrides remain intact except where an explicit cancel/delete onward command overrides them.

### 7.3 Concrete recurrence acceptance example

Start with a Monday 07:30 class titled A from 16 November 2026. Customize the occurrence in the week of 30 November to title B. Pre-schedule default C from 14 December. Set default D in the week of 23 November.

Expected: week of 16 November stays A; 23 November is D; 30 November stays B; 7 December is D; 14 December and later use C. Promoting the 30 November override with Set Default removes that week's redundant override and makes B the default until 14 December. Canceling only 7 December leaves that canceled occurrence visible; an independent replacement can occupy its cell. Deleting the original series from 14 December removes its future instances/overrides but not the replacement or earlier history.

## 8. Implementation contracts and engineering defaults

These are implementation defaults selected to make the handoff actionable. They do not authorize unrelated product expansion.

### 8.1 Data representation and storage

- Extend the existing event system rather than creating a separate timetable database. Persist class series and their revision/override state together with ordinary event records in the existing events JSON store. A class is a discriminated event kind; regular records retain categories and classes use no ordinary category. Legacy School remains a read-compatible value restricted from new ordinary-event creation.
- Add highlight state, class kind, canceled status where applicable, and optional class schedule state. Class schedules contain effective-from-week default revisions, optional end limits, full weekly overrides keyed by original week, and explicit cancellation/deletion cutoffs/tombstones. Keep stable record IDs; derive occurrence keys from record ID plus original week. Do not save a generated database row for every future occurrence.
- Define EventOccurrence separately from stored EventItem: base event/series ID, stable occurrence key, original week for classes, resolved fields, actual start/end, highlight state, and status. UI lists/calendars consume occurrences; edits use base identity plus occurrence/scope information.
- Add a public collection transaction method at the storage boundary, reusing JsonFileStore's file lock, atomic replacement, and last-valid backup behavior. Conflict validation plus mutation must observe the same locked snapshot. Reject stale updates using an expected record revision; keep user input for conflict resolution.
- Use pure domain functions for timezone-aware week keys, effective-default selection, occurrence resolution, collision checks, interval membership, and count/highlight eligibility. No filesystem or UI dependencies in these functions.
- Retain ordinary event recurrence metadata for compatibility; v3.1's new recurrence execution is specifically for Class schedules. Do not silently reinterpret old School records as recurring schedules.

### 8.2 API/client changes

- Preserve existing ordinary event CRUD endpoints and envelopes while extending validation/types. Preserve no-query GET /api/events as stored-record access for compatible clients and draft source lookup.
- Add GET /api/events/occurrences with required `from` and `to` local-date bounds, using a half-open date interval in Asia/Saigon. Return resolved occurrences intersecting the interval, including canceled entries, with stable identifiers. Bound each request to at most 366 days; clients request adjacent ranges as needed.
- Add a scoped class-occurrence mutation endpoint under /api/events/[id]/occurrences. Its validated command carries action (edit/cancel/delete), original week, scope (this-week/this-week-onward), expected revision, and fields for edits. An edit with onward scope creates the effective default revision described above; cancel/delete have their explicit rules. Existing DELETE on a recurring class must not silently erase its entire history: require scoped semantics.
- Ordinary and single-class creation use extended POST /api/events. A recurring class create includes its starting default/end date. Return the base record and relevant resolved occurrence; use existing error envelopes for validation, missing records, and conflict responses.
- Extend query keys with occurrence date ranges. Invalidate all affected Events records, occurrence windows, highlights/counts, and drafts on successful mutations. Keep API calls in client modules and use shared domain predicates across displays.
- Extend event drafts with class kind/schedule fields, highlight, optional end time, original-week/scope, and source revision. Key class edit drafts by series plus occurrence and scope, so two weeks cannot overwrite each other's drafts. Revalidate availability, source revision, and recurrence rules on publish. Preserve publication idempotency and old draft compatibility.
- Keep existing local recovery versus saved draft distinctions. After a publication failure, retain the draft and user input. Publishing the same successful draft again must not create a second class series.
